## NTHN Linux environment (separate `com.nthn` app)

The real Linux environment is delivered by the independent `srrnthn3-a11y/rea-termux-analysis` repository, not by the dashboard. That app is a fork of Termux `v0.119.0-beta.3` with application id `com.nthn`, ARM64-only ABIs, and the real Termux terminal, PTY, session and package implementations. It embeds a custom bootstrap compiled from pinned `agnostic-apollo/termux-packages` with `TERMUX_APP__PACKAGE_NAME="com.nthn"`. The dashboard remains a separate Capacitor app (`com.nthnentps.dashboard`) and does not execute shell commands from its WebView.

The custom bootstrap workflow (`.github/workflows/build-separate.yml`) previously failed at `libtirpc-1.3.6` because its tarball ships `INSTALL` as an absolute symlink to `/usr/share/automake-1.16/INSTALL` while the custom Automake was installed under `/usr/local`. Commit `288cba6` populates the system Automake data path, adds `git`, `python` and `nodejs` to `PACKAGES_POST_ADDITIONAL_LIST`, and extends `verify_bootstrap.py`. Run `41654652900` then reached Node.js but failed because the host ICU build inherited the bootstrap's Android cross-compile flags. Commit `fead949` adds `scripts/patch_nodejs_hostbuild.py`, which isolates the ICU host build in a subshell. Workflow run `41766590366` is the verification run; it had not completed at the time of this update.

The device has no root, `su` or `adb`, so APK installation requires user confirmation. Official Termux repository packages hard-code `/data/data/com.termux/files/usr` and are not directly compatible with the `com.nthn` prefix; arbitrary `apt install` from that repository will produce broken paths. A package must be built for `com.nthn` or used inside a proot rootfs. The repository includes `scripts/test_bootstrap_proot.sh`, which binds an extracted bootstrap to `/data/data/com.nthn/files` and runs the real ARM64 binaries under proot, including a locally built `.deb` install test. The method was validated end-to-end against the upstream Termux bootstrap: real ARM64 `bash`, `apt`, `dpkg`, file persistence and `.deb` install/purge passed. This is a runtime test, not an APK install.

The dashboard's latest verified CI APK is `app-debug.apk`, 4,528,413 bytes, SHA-256 `07a970655e21de2f174391a730f346053155f11528647e3ff7d21473d3a9c591`. ## Android browser — AI Providers fetch receiver fix

The Android “Failed to execute 'fetch' on 'Window': Illegal invocation” error was caused by AiClient storing native fetch and invoking it as this.#fetch(...). That method call supplied the AiClient instance as the receiver instead of Window, so browser receiver validation failed before the request reached /api/ai. The resulting API-unavailable UI was a client-side failure, not a backend startup, route, authentication or cache error. Inspection found Alex's existing fetch calls use direct global invocation and do not share this defect.
