# Jef V1.9 agent architecture

## Goal

Extend the real `com.nthn` Jef service with research, durable knowledge,
bounded task execution, environment inspection, and a verifiable development
workflow. Preserve V1.8 chat, provider accounts, workspace confinement, and
approval behavior. The editable `~/nthnEntps` source is distinct from the
running service.

## Existing boundaries

- `agent.ts` owns the model/tool loop, streamed progress, approval tickets,
  cancellation, and step limit. `tools.ts` owns the tool registry and confined
  `proot` runner. The mobile CLI is a fresh Node process per request.
- `memory.ts` stores up to 500 keyword matched JSON memories. The mobile CLI
  selects a project within `com.nthn` Linux home and stores private state in
  `.local/agent`. The Android WebView loads `nthn_chat.html` from APK assets.
- The APK bundles the Node agent files. `~/nthnEntps` is installed once and
  preserved, so source edits do not alter the current runtime.

## V1.9 design decisions

1. Research tools live in the Node agent and use HTTPS, bounded responses,
   public-address validation, redirect validation, and explicit citations.
   Search providers are configurable; URL retrieval works independently of a
   search provider. No credential is embedded in prompts or tool results.
2. Memory moves to SQLite in app-private storage with a one-time JSON import.
   Keep the existing memory API and scopes. Use FTS for local retrieval and
   optional embeddings only when configured; no paid dependency is required.
   Preserve history and export/delete controls. Extract candidate memories
   from completed conversations through a bounded, reviewable rule set.
3. Existing agent loop remains the execution engine. Add persisted task state,
   steps, retries for transient read-only tools, progress logs, and explicit
   autonomy policy. The default is supervised. Autonomous mode can be enabled
   only for bounded read-only actions; file changes and executable commands
   still require approval unless the user grants an exact, expiring scope.
4. New system tools inspect the selected workspace and app-owned processes.
   They do not claim access to the Android OS or open interactive terminal.
   Android bridges are added only for capabilities the native app can supply.
5. Self-development can inspect the bundled project, propose source edits,
   run local tests and prepare a release manifest. Producing an installable
   APK requires CI or a local Android toolchain and a stable signing identity.
   Installation uses Android's package installer with user confirmation;
   rollback keeps a verified previous artifact. No runtime source rewrite is
   treated as an installed app update.

## Integration limits

- Web search requires a configured provider endpoint or key; direct URL
  retrieval requires network access. Local embeddings require a compatible
  local model and enough device memory. Online embeddings require credentials.
- V1.7 and V1.8 APKs have the same signing certificate (SHA-256
  `b6da01480eefd5fbf2cd3771b8d1021ec791304bdd6c4bf41d3faabad48ee5e1`).
  V1.9 must retain that identity for in-place upgrades. The current debug-key
  distribution model still needs a separate production signing policy.
- Jef's native Android shell and packaged UI are not hot-swappable. An APK
  update is required for native code, manifest permissions, and bundled UI.

## Verification

Each module needs a failing test before implementation, a focused passing
test, integration tests at the CLI/tool boundary, typecheck, and a release
build. Live network and Android installation must be tested on a device or CI
with the required credentials; offline fixtures cannot prove those effects.
